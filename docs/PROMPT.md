# 弾幕メーカー iOS版 開発プロンプト（0 → App Store 審査提出まで）

あなたはこのプロジェクトのシニアエンジニア兼メンターです。私（Koshin）はプログラミング未経験から Claude Code と一緒に iOS アプリ（トレカダッシュ）をリリースした個人開発者です。
このリポジトリで、弾幕ステージをユーザーが作って投稿し、世界中で遊び合える iOS ゲーム「弾幕メーカー」を、ゼロから App Store の審査提出直前まで作ってください。

同じフォルダに次の2つを置いています。作業前に必ず全部読んでください。

- `SPEC.md` … 仕様書。仕様の正はこれ。迷ったらここに戻る
- `prototype.html` … ブラウザ版の試作。ゲームの手触り（弾の動き、当たり判定、操作感、エディタのプレビュー）の正はこれ。iOS 版はこれと同じ感覚で遊べること

---

## 0. 進め方のルール（全フェーズ共通）

1. **フェーズごとに止まる。** 各フェーズの最後に「やったこと / 動作確認の結果 / 私がやる作業 / 次のフェーズでやること」を短く報告し、私の OK を待ってから次へ進む
2. **私がやる作業は、具体的な手順で頼む。** どの画面のどのボタンを押すか、何をコピーしてどこに貼るかまで書く。専門用語には一言で説明を付ける
3. **テスト結果をごまかさない。** 失敗したテストを消したり、条件を緩めて通したりしない。通らないなら理由を報告する
4. **詰まったら止まって相談する。** 同じエラーで3回試して直らなければ、原因の仮説と選択肢を出して私に聞く
5. **マイルストーンごとに git commit。** メッセージは日本語で何をしたか分かるように。GitHub へは私が OK したときに push
6. **Cloud Functions のデプロイ前は必ず ESLint とテストを通す**
7. **お金がかかる操作・本番環境への変更は事前に確認を取る。** Firebase の本番デプロイ、課金プランの変更、有料サービスの登録など
8. **秘密情報を読まない。** `.p8` などの秘密鍵、API キーの中身は表示・読み込みしない。必要な場所への登録は私が手作業でやるので、手順だけ教える。秘密情報を含むファイルは `.gitignore` に入れる
9. **トレカダッシュのコード・Firebase プロジェクト（cardalerthub）には一切触らない。** このアプリは新しい Firebase プロジェクトで作る
10. **最後の「審査へ提出」ボタンは私が押す。** あなたは押す直前まで準備する

## 1. 使ってほしい道具

| 用途 | 道具 |
|---|---|
| Xcode プロジェクト生成 | XcodeGen（`project.yml` で管理し、`.xcodeproj` を手で触らない） |
| ビルド・テスト | `xcodebuild`、`xcrun simctl` |
| iOS の UI テスト・スクリーンショット | XCUITest |
| Web 部分（共有ページ・OGP・規約ページ）の確認 | **Playwright**（`@playwright/test`）。Firebase エミュレーターに対して E2E テストを書く |
| 画面の目視確認 | Playwright MCP が使えるなら、共有ページや規約ページを実際に開いてスクリーンショットで確認。iOS は `simctl io booted screenshot` で撮って自分で見る |
| バックエンド | Firebase CLI、Firebase Emulator Suite（Firestore / Functions / Auth / Hosting / Storage） |
| App Store Connect | 基本は App Store Connect API（fastlane など）。API キーの登録は私がやる。API でできない画面操作は、私がログインしたブラウザで Playwright MCP を使って一緒に進める |

Playwright は iOS アプリ本体のテストには使わない（そこは XCUITest）。Web まわりと、ブラウザでしかできない管理画面の作業に使う。

## 2. フェーズ

### フェーズ0：環境確認

- `xcodebuild -version` が Xcode 26 以上か確認。**26 未満なら作業を止めて報告**（今の App Store 提出には Xcode 26 / iOS 26 SDK でのビルドが必要）
- Node.js、Firebase CLI、XcodeGen、Playwright、git、gh の有無を確認し、足りないものはインストール手順を提示（Homebrew や npm でインストールしてよいか私に確認）
- 確認できたら、全フェーズの作業計画をざっくり出す

### フェーズ1：プロジェクトの土台

- XcodeGen で iOS アプリを作成。対象は iOS 17 以上、iPhone のみ、縦画面のみ
- 構成：
  - `DanmakuCore`（Swift Package）… シミュレーション本体。UIKit/SpriteKit に依存しない純粋な Swift
  - `DanmakuApp` … SwiftUI のアプリ本体
  - `firebase/` … Functions（TypeScript）、セキュリティルール、Hosting
  - `web-tests/` … Playwright のテスト
- バンドル ID は `com.koshin.danmakumaker`（変える場合は私に確認）
- String Catalog を最初から用意し、UI 文字列は日本語・英語の両方をここに入れる。ハードコードした文字列を画面に出さない
- README に「ビルドの仕方」「エミュレーターの起動の仕方」「テストの回し方」を書く

### フェーズ2：DanmakuCore（最重要）

- `prototype.html` の `emit` / `step` / ボス関連の処理を Swift に移植
- SPEC の「3.4 再現性」を厳守：固定ステップ 1/120 秒、シード付き乱数のみ、描画と計算を分離
- ステージ形式（`SPEC.md` 7章の `emitters`）の Codable モデルと、値の範囲を丸める `sanitize`
- リプレイ：各ステップの自機移動量を記録・圧縮・復元する仕組み
- テスト（XCTest）：
  - 同じステージ＋同じ入力で、何回回しても弾の数・被弾したステップ・結果が完全一致する
  - リプレイを保存→復元→再生して、元のプレイと同じ結果になる
  - 各パターン（放射・渦巻き・自機狙い・雨・首ふり扇）で、試作と同じ角度・速度で弾が出る（試作の計算式から期待値を作る）
  - ボス戦の段階切り替え、弾の全消去、時間切れ
  - 弾数上限 1600 で止まる
- 性能：弾 1600 発で 1 ステップの計算が十分速いこと（ベンチマークテストを置く）

### フェーズ3：プレイ画面

- SpriteKit で描画。論理画面 360×540 を端末に合わせて拡大
- 操作：画面のどこでもドラッグで相対移動（倍率 1.2）
- 弾の見た目・自機・ボス・HP バー・READY 表示・段階表示・発射台の印の出し方（撃ち始める 0.6 秒前から点滅）は試作と同じ
- 結果画面：クリア / 被弾 / 時間切れ、もう一度、戻る
- 確認：シミュレーターで実際に遊べる状態にし、スクリーンショットを撮って自分で見て崩れがないか確認。iPhone SE サイズと 6.9 インチの両方で確認
- 古めの端末を想定し、弾 1600 発で 60fps を保てるか Instruments かフレーム計測で確認し、結果を報告

### フェーズ4：エディタ

- SPEC 4章のとおり。発射台カードごとのループプレビュー（SpriteKit の小さいビュー、または `TimelineView`＋`Canvas`）
- 内容を変えたらクリア確認をリセット。テストプレイでクリアしたら投稿ボタンが押せる
- 作業中のステージは端末に下書き保存
- XCUITest：発射台の追加・削除、パターン変更、テストプレイ→（テスト用の無敵フラグでクリア）→投稿ボタンが有効になる流れ。無敵フラグは DEBUG ビルドでのみ有効にする

### フェーズ5：バックエンド

- 新しい Firebase プロジェクトを私に作ってもらう（手順を出す）。リージョンは asia-northeast1
- Firestore のデータ構造・Cloud Functions は SPEC 7章のとおり。クライアントから `stages` への直接書き込みはルールで禁止
- `publishStage` の入力検証：値の範囲、発射台数、ステージ名の文字数、NG ワード（日本語・英語のリストを `firebase/functions/src/ngwords/` に置く）、クリアリプレイの有無
- 短縮 ID：紛らわしい文字（0/O、1/I/L など）を除いた5文字
- ESLint、Functions の単体テスト、セキュリティルールのテスト（`@firebase/rules-unit-testing`）を全部エミュレーターで通す
- **予算アラート**を設定する手順を私に出す（月 1,000 円で通知など）
- 本番デプロイは私の OK を取ってから

### フェーズ6：認証・一覧・投稿・いいね・通報・ブロック

- 遊ぶだけは匿名認証。投稿・いいね・通報は Sign in with Apple（匿名アカウントからリンク）
- Sign in with Apple の鍵の作成と Firebase への登録は私がやる。手順だけ出す
- 世界のステージ：人気 / 新着 / 高難度 / 急上昇、ID 検索、ステージ詳細（通報・ブロック・いいね・シェア）
- 一覧取得には必ず件数制限とページングを付ける（読み込み回数の暴発を防ぐ）
- 挑戦・クリアの結果は端末でまとめて `submitResults` で送る
- 投稿前に利用規約への同意画面
- ブロックした作者のステージは一覧に出さない

### フェーズ7：共有

- SPEC 6章のとおり。Hosting の `/s/**` を `sharePage` 関数に向け、OGP 付き HTML を返す
- `apple-app-site-association` を配信し、ユニバーサルリンクでアプリの該当ステージを開く
- 投稿時に OGP 画像（1200×630）を生成して Storage に保存
- シェアボタン：作者向け・プレイヤー向け（クリア / 撃破 / 失敗）の文言を日英で。`ShareLink` と X の投稿用 URL
- **Playwright で E2E テスト**（エミュレーター相手）：
  - `/s/{存在するID}` で、`og:title` `og:description` `og:image` `twitter:card` が正しく入っている
  - OGP 画像の URL が 200 を返し、画像サイズが 1200×630
  - `/s/{存在しないID}` で、分かりやすい「見つかりません」ページになる
  - 日本語・英語の表示切り替え（`Accept-Language`）
  - スマホ幅でレイアウトが崩れない（スクリーンショットを撮って自分で確認）
  - `apple-app-site-association` が正しい Content-Type と内容で返る

### フェーズ8：広告・課金

- AdMob：リワード広告で「その場から復活」（1プレイ1回まで）。開発中は必ずテスト広告 ID を使う
- 広告を出す前の同意（UMP SDK）とトラッキング許可（ATT）の流れを入れる
- RevenueCat：広告削除の買い切り（非消耗型）。購入者は復活が無料・無制限、広告を一切出さない。購入の復元ボタンを置く
- App Store Connect のアプリ内課金の登録手順を私に出す
- ステージ開始ごとのインタースティシャル広告は入れない

### フェーズ9：サンプルステージとローカライズの仕上げ

- 公式サンプルステージを 30 本、易しい→難しいの順に作る（耐久とボスを混ぜる）。データは JSON でリポジトリに置き、初回起動時に表示
- クリアできるかの最終確認は私が遊んでやる。あなたは各ステージに「想定難易度」と「狙い」のメモを付け、私がチェックしやすい一覧を作る
- 日本語・英語の文言を全画面で見直す。英語はネイティブが読んで自然な、短いゲームらしい文言に

### フェーズ10：規約・サポートページ

- Hosting に、利用規約・プライバシーポリシー・サポートページを日英で作る
  - プライバシーポリシーには、匿名認証・Sign in with Apple・AdMob・RevenueCat・Firebase で集めるデータを正確に書く
  - 利用規約には、投稿されたステージの扱い、禁止事項、通報への対応、アカウント停止を書く
  - サポートページに連絡先を載せる（メールアドレスは私が決める）
- Playwright でリンク切れがないこと、スマホ幅で読めることを確認
- アプリの設定画面からこれらのページと連絡先に飛べるようにする

### フェーズ11：仕上げのテスト

- 全テストを回す（DanmakuCore、XCUITest、Functions、ルール、Playwright）
- 機内モード・電波が弱いときの挙動（一覧の読み込み失敗表示、投稿の再試行）
- 初回起動から「ステージを1つ遊ぶ → 作る → 投稿 → 共有」まで XCUITest で通す
- アプリサイズ、起動時間、メモリを確認して報告
- 審査で落ちやすい点の自己チェックリストを作って報告：
  - UGC 対策（通報・ブロック・NG ワード・規約同意・連絡先）
  - 広告がゲーム操作の邪魔をしない
  - 購入の復元がある
  - ログインなしで遊べる（投稿時だけログイン）
  - アカウント削除機能（Sign in with Apple を使うので必須。設定画面に置き、Firestore のユーザーデータと投稿も削除するか非公開にする）

### フェーズ12：App Store 提出準備

- **スクリーンショット**：XCUITest＋`simctl` で、6.9 インチの必須サイズを日英それぞれ撮る。弾幕が画面いっぱいに出ている見栄えのいい場面を選ぶ。キャプション入りにするなら、文言案を先に私に見せる
- **メタデータ**（日英）：アプリ名、サブタイトル、説明文、キーワード、プロモーション用テキスト。案を出して私が決める
- **App Store Connect の設定**（API でできるものは API、無理なものは私がログインしたブラウザで Playwright MCP を使って一緒に進める。どちらの場合も入力内容は先に私に見せる）：
  - App プライバシー（データ収集の回答。AdMob と Firebase の実態に合わせる）
  - 年齢制限の質問（ユーザー生成コンテンツあり）
  - 輸出コンプライアンス
  - 配信地域：**中国本土を除外**
  - 価格：無料、アプリ内課金の紐付け
  - 審査メモ：「ログインなしで遊べる。投稿の確認は Sign in with Apple で可能」など、審査員が迷わない説明を日英で
- **ビルド**：Xcode Cloud（または `xcodebuild archive`）で Release ビルド → TestFlight へ。署名まわりで私の作業が必要なら手順を出す
- TestFlight で私が実機確認したら、審査提出の直前の状態まで整えて報告。**「審査へ提出」は私が押す**

## 3. 最初の一手

まず `SPEC.md` と `prototype.html` を読み、分からない点・仕様の矛盾・決めてほしいことを箇条書きで出してください。そのあとフェーズ0から始めてください。
