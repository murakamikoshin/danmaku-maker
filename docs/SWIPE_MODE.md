# スワイプ弾幕 仕様書（実装用）

世界のステージから「一番盛り上がる10秒」を切り出し、縦スワイプで次々に遊ぶモード。1プレイ = スタミナ1、被弾で終了。
**手ざわりと演出は、ブラウザ試作 `docs/swipe_prototype.html` と同じにする。** この文書の数値はすべて試作から写したもの。迷ったら試作のコードが正解。

- 表記：論理画面は 360×540（本編と同じ）。座標・大きさは論理 px、時間は秒
- 「（演出）」と付いたものは描画だけで、当たり判定や記録に関わらない
- アプリ内では「スワイプ弾幕 β」として出す。Remote Config `swipe_enabled` で出し入れする

---

## 1. 画面の流れ（状態）

```
タイトル ──スタート──▶ [スタミナ確認] ─足りない─▶ スタミナ切れ画面
                          │使う(−1)
                          ▼
     ┌──────────▶ 切り替え(0.3秒) ─▶ GO(0.5秒) ─▶ プレイ(10秒)
     │                                              │        │
     │                                           生き残る   被弾
     │                                              ▼        ▼
     └────── 自動0.9秒 / 上スワイプ / タップ ──── クリア     失敗(1.45秒)
                                                              │自動 / 上スワイプ / タップ
                                                              ▼
                                                         プレイ終了画面 ─もう1回─▶ [スタミナ確認]
                                                              └─やめる─▶ タイトル
```

| 状態 | 長さ | 中身 |
|---|---|---|
| 切り替え | 0.3 秒 | 前の画面が上に抜け、次のクリップが下から入る。動きは `1 − (1 − p)³`。切り替え音（演出：ノイズ 0.18 秒、低域フィルタ 900→3000Hz、音量 0.12） |
| GO | 0.5 秒 | 弾は止まっている。自機は動かせる。画面を 25% 暗くし、「GO!」を出す |
| プレイ | 10 秒 | 計算を進める。最初の 0.7 秒はバリア（GO と合わせて 1.2 秒） |
| クリア | 1.05 秒（自己ベスト更新時 1.6 秒） | 画面は動き続ける。終わったら次のクリップへ。指が触れている間は進まない |
| 失敗 | 1.45 秒 | 最初の 0.5 秒はスローモーション（速さ 0.16 倍）。終わったらプレイ終了画面へ |
| プレイ終了 | 押すまで | 結果とスタミナを出す |

## 2. 操作

| 場面 | 操作 | 動作 |
|---|---|---|
| GO・プレイ | ドラッグ | 自機の移動（本編と同じ倍率 1.2 の相対移動。端から 6 px 以内には行かない） |
| GO・プレイ | 右上「スキップ ›」 | 次のクリップへ。**連続は 0 に戻る**（トーストで「スキップしたので、連続は0に戻りました」） |
| クリア | 上スワイプ（40 px 以上）／タップ（14 px 未満の動き） | すぐ次へ |
| 失敗 | 上スワイプ／タップ | すぐプレイ終了画面へ |
| クリア | 画面下に「↑ スワイプで次へ」を上下に揺らして出す（1 秒周期、5 px） | |

スワイプで次へ進むのは結果の表示中だけ（プレイ中のドラッグとぶつからないように）。

## 3. 1本のクリップ

### 3.1 当たり判定とバリア
- 被弾：本編と同じ（自機の判定点と弾の中心の距離が 5.5 未満。レーザー・巨大弾などは本編の判定）
- バリア中は被弾しない。ライフ制・HP 制のステージでも、このモードでは 1 回被弾で終わり
- ボス戦でもボスを倒す必要はない。10 秒生き残ればクリア

### 3.2 途中から始める
- サーバーが決めた `clip.at`（4 章）まで、自機を初期位置（180, 459）に置いたまま、無敵で早送りする（描画なし）
- 早送りが終わったら、自機を一番安全な場所に置く：
  - 候補点：x = 30 + 300/11 × i（i = 0〜11）、y = 270 + 226.8/7 × j（j = 0〜7）の 96 点
  - 各候補点について、すべての弾の「今・0.3 秒後・0.6 秒後」の位置（今の速度のまま進めた位置）までの最短距離を求める
  - 点数 = 最短距離 − |x − 180| × 0.03 が一番大きい点を選ぶ。点数は 0.01 px に丸めて比べ、同点なら先に調べた点（左から、上から）を選ぶ（三角関数の最後の桁の違いで、アプリとサーバーの選ぶ場所が分かれないようにする）
  - ビームは光線までの距離（ためている間も同じ）、爆風は縁までの距離で見る。弾が 1 つもなければ、真ん中に近い一番上の点
- 次の 2 本は裏で早送りしておく

### 3.4 計算の決まり（アプリとサーバーで同じにする）
アプリ（`Simulation(swipeStage:)`）とサーバーは、次の手順で**同じ状態**から始める。

- **作り方**：ライフ 1（ステージのライフ・HP の設定は使わない）。自機はショットを撃たない。ボスの場面（ボス戦、連戦のボスの場面）は「ダメージ勝負」と同じ扱い（HP は無限でボスは倒れない。「第N段階」は時間の 3 分の 1 ずつで進む）。乱数の種は元のステージと同じ
- **早送り**：ステップ `144 + at × 120`（READY の 144 ステップ + 開始から `at` 秒）まで、自機を初期位置から動かさず、無敵で、かすりを数えずに進める
- **置く**：3.2 章の安全な場所に自機を置き、バリアをつける。バリアは**遊び始めてから 84 ステップ**（GO の間は減らさない）
- **GO**：60 ステップ。弾も時間も止めたまま、自機だけをその間の操作で動かす
- **遊ぶ**：1200 ステップ。生き残ればクリア。ボムを出したら画面の弾（ビーム・爆風も）を全部消し、次の 120 ステップのバリアをつける
- コードは `DanmakuCore` の `SwipeClip.prepare`、`Simulation` の `fastForward` / `place` / `nudgePlayer` / `giveShield` / `clearBullets`。サーバー（TypeScript）は同じ手順を `fullsim.ts` に書く

### 3.3 難しさの並べ方（ランダム、ただし序盤は易しく、だんだん難しく）
試作では連続数に合わせて弾幕を自動で作っている。本番はステージを作れないので、**連続数に合わせて、ランダムに選ぶクリップの難しさを上げていく**。

- 目標のクリア率 = `max(8%, 85% − 連続 × 4%)`（連続 0：85%、5：65%、10：45%、15：25%、20 以上：8%）。**難しさは千分率の整数**（クリア率 85% = 850）で扱う（小数の端数で、アプリとサーバーの選ぶクリップが分かれないように）
- 候補の一覧（10 章）から、自分・ブロックした作者・このプレイで出したクリップを除く → 難しさが「目標 ± 100（10%）」に入るものを集める。20 本未満なら ± 200、それでも足りなければ目標に近い順（同じ近さなら 難しさ → ID の順）に 20 本
- 集めたものを 難しさ → ID の順に並べ、そのプレイの乱数で 1 本選ぶ。選べるものがなければ公式ステージに切り替える
- 乱数：`Mulberry32(seed + index × 0x9E3779B9)` の最初の 1 つ（`index` はそのプレイの何本目か。0 から。スキップした分も数える）。選ぶ位置は `floor(乱数 × 集めた本数)`
- 実装：`DanmakuCore` の `SwipeFeed.pick`
- 難しさ：
  - クリップの挑戦が 10 回以上 → `clipClears / clipPlays`
  - それ未満（新しいステージ）→ 切り出した区間の弾の平均数からの見積もり（`clip.est`、4 章）。β で実際のクリア率と比べて式を直す

## 4. クリップの切り出し（サーバー）

```
stages/{id}
  clip: { at: number, est: number, v: 1 }   // 開始秒（0.5 秒刻み）、見積もりのクリア率（0〜1）、選び方の版
  clipPlays: number
  clipClears: number
```

- `publishStage` の中で、スワイプ用の計算（3.4 章）で、自機を初期位置から動かさず無敵で最後まで進め（`fullsim.simulate` の `observe`）、0.5 秒ごとに画面内の弾の数を数える
- 10 秒の区間で平均が一番大きい区間を選ぶ。除外：開始 2 秒以内、連戦の場面転換（切り替えの間）をまたぐ区間。スワイプ用の計算ではボスは倒れないので、「ボスを倒した後」の区間はない
- ステージが 10 秒なら `at = 0`。平均 15 発未満なら `clip` を作らない（フィードに出さない）
- `est`（見積もりのクリア率）：最初は `clamp(1.1 − 平均弾数 / 250, 0.05, 0.95)`。挑戦 10 回以上になったら実際のクリア率を使うので、この値は新しいステージのときだけ使う
- 既存ステージは `backfillClips`（一度だけ流す関数）で計算する
- テスト：`DanmakuCore` で同じ区間を選ぶこと、`at` まで早送りした後の弾の数がサーバーと一致することを確かめる

### 4.1 クリアできないクリップは流さない
ステージ全体は作者がクリアしているが、クリップは**途中から・作者と違う位置で**始まる（自機狙いの弾の向きも作者のときと変わる）。そのため「この始め方では避けられない 10 秒」が起こり得る。これを必ず防ぐ。

- 区間を選んだら、**本番と同じ始め方**（`at` まで早送り → 安全な位置 → バリア 0.7 秒。GO 中は動かない）で、ボットに 10 秒遊ばせる
- ボットは `StageBot` の「強いボット」と同じ：1 ステップの移動は最大 7 単位（1.75 px、約 210 px/秒＝人間の指で出せる速さ）、9 方向から 40 ステップ先読みして選び、6 ステップ続ける
- **ボットがクリアできた区間だけ**を `clip` にする。クリアできた操作記録を「クリアできる証拠」として保存する（`clipProofs/{stageId}`、サーバーだけが読める）
- クリアできなければ、盛り上がりが 2 番目〜5 番目の区間で順に試す。どれもだめなら `clip` を作らない
- ボットがクリアしたときの「弾との一番近い距離の平均」も記録し、`est`（見積もりのクリア率）を直す材料にする
- ボットは TypeScript に移す（`fullsim.ts` を 1 ステップずつ進められて、状態を複製できる形にする）。`StageBot` と同じ動きになることをテストで確かめる
- 念のための見張り：挑戦 50 回以上でクリア率 3% 未満のクリップは、候補の一覧（10 章）から自動で外し、ログに出して見直す
- スワイプ中の「通報」にも、本編と同じ「クリアできない」を選べるようにする

試作（`docs/swipe_prototype.html` の `botClears`）でも同じボットで確かめている。試作の弾幕では、易しいうちは全部、連続 15 以上でも 9 割が通った（だめなものは別の弾幕に作り直す）。1 本あたりの確認は 0.1〜0.5 秒。

## 5. 点数

計算はすべて**上限なしの整数**（9 章）。ランキングのため、点数はサーバーでリプレイから計算し直せるようにする（15 章）。そのため、点数に関わる時間はすべてステップ数（1/120 秒）で数える（コンボが切れる 1.5 秒 = 180 ステップ）。

| 名前 | 式・値 |
|---|---|
| かすり | 弾の中心が自機の判定点から 18 px 以内に入ったら 1 かすり（弾 1 発につき 1 回）。巨大弾・広がる弾は当たり判定が大きいので、「**その弾の当たり判定 + 12.5 px**」にする（ふつうの弾は 5.5 + 12.5 = 18。でないと、かする前に当たってしまう）。ビーム・爆風はかすりの対象にしない。当たる弾も、当たる手前で 1 回かすったことになる。早送りの間は数えない |
| コンボ | クリップごとに 0 から。前のかすりから 180 ステップ（1.5 秒）未満なら +1、それ以上空いたら 1 から。180 ステップかすらなければ、そのステップの最後に 0 に戻る |
| 段階 `lv` | `min(8, 1 + floor(コンボ / 8))`（色や演出の強さに使う） |
| かすりの点 | `100 × 2^floor(コンボ/8) × (8 + コンボ mod 8) / 8 × 3^連続`（割り算は整数の切り捨て） |
| 倍率の表示 | `2^floor(コンボ/8) × 3^連続` |
| ボムのゲージ | かすり 1 回で +1。40 に届いたらその場でゲージを 0 に戻し、**そのステップの弾の処理が終わった後に**ボムを出す（弾を調べている途中で消さない）。ゲージはクリップをまたいで持ち越す。プレイ開始で 0。被弾したステップではボムは出さない |
| 金の粒 | 1 個 = そのときのかすりの点 ÷ 2。**ボム・クリアの瞬間に、画面の弾の数 × その値をまとめて加点する**（粒が飛んで吸い込まれるのは見た目だけ）。弾の数は、そのステップの弾の処理が終わった後の数。コンボと連続はそのときの値（クリアのときは連続 +1 の後）。最後のステップでは、ボム → クリアの順に処理する |
| クリア点 | `100 × 500 × 2^floor(コンボ/8) × 3^(連続+1)`。その後で連続 +1 |
| 連続 | クリアで +1。被弾・スキップで 0 |
| プレイの点数 | プレイ開始で 0。プレイ終了画面に出す |

目安：連続 15 前後で兆、連続 120 前後で無量大数に届く。

### 5.1 点数の表示
- 全部の桁を日本語の単位で出す：`1兆6532億3141万3424`
  - 4 桁ごとに 万・億・兆・京・垓・𥝱・穣・溝・澗・正・載・極・恒河沙・阿僧祇・那由他・不可思議・無量大数（10^68）
  - 0 の 4 桁は飛ばす（`1億0000万5` ではなく `1億5`）
  - 10^68 以上は、上の部分を同じ書き方で書いて「無量大数」を付ける：`1万2345無量大数7`、`3万無量大数無量大数`
- 短い書き方（かすりの「+点」、倍率、自己ベスト）：一番上の単位で、100 以上は整数、10 以上は小数 1 桁、10 未満は小数 2 桁（末尾の 0 は消す）。例 `4.5億`、`1.23万無量大数`
- **英語の画面**（端末の言語が日本語以外）：
  - 全部の桁：3 桁ごとのカンマ区切り。例 `1,653,231,413,424,424`
  - 短い書き方：`K` `M` `B` `T` `Qa` `Qi` `Sx` `Sp` `Oc` `No` `Dc`（10^33）。それより上は、上から 3 桁を使った指数表記 `1.23e72`（上限なし）。小数の付け方は日本語と同じ（切り捨て）
  - 例：`1.23K`、`1.65Qa`、`16.5Qa`、`999Dc`、`1e36`、`3e140`
- 画面右上の点数は、22 px で幅 280 px を超えたら、収まるまで文字を小さくする（下限 6 px）
- 表示する点数は本当の点数へ毎フレーム「差 × min(1, 経過秒 × 12)」ずつ近づく（カウンターが回る）。回っている間は金色で光らせる

| 自己ベスト更新（連続数） | 「NEW RECORD」34 px 金 1.4 秒（初めての記録では出さない） | 1319Hz・1760Hz | |
| 被弾 | 自機が弾けて粒 60 個。赤い輪。赤フラッシュ 0.7、揺れ 16。スローモーション 0.5 秒（周りを暗くする）。「あと X.X 秒」44 px ピンク。連続 2 以上なら「N 連続で終了」 | ノイズ 0.5 秒（1800→80Hz）＋のこぎり波 220→55Hz | `.heavy` を 3 回 |

大きい文字の出方（共通）：0.1 秒で 0.3 倍 → 1.4 倍に広がり、その後 1 倍に戻る。最後の 25% で消える。出た直後だけ小さく左右に揺れる。
揺れは毎秒ほぼ 0 まで減り、フラッシュも素早く消す。「視差効果を減らす」がオンなら、揺れは 25%、フラッシュは 40% にする。

### 6.3 描き方
- 弾：外側に半径 2 倍の光（不透明度 0.28、加算合成）、本体、中心に白（半径 0.5 倍）。色ごとにまとめて描く
- 自機：水色の三角（光つき）、白い判定点（半径 2.6）、後ろに揺れる橙の炎。バリア中は白い輪が点滅
- 発射台の印：色の円（脈打つ）と回る四角。雨は印なし
- 金の粒：金の円（半径 3.5、光つき）に白い点。散ってから 0.15 秒後に自機へ引き寄せる（加速 3200、毎フレーム 0.9 倍に減速）、12 px 以内で取る
- SpriteKit では弾・粒・火花をノードの使い回し（プール）で描く。弾の数は本編と同じ上限

### 6.4 音
試作の音は全部その場で作っている（矩形波・三角波・のこぎり波・ノイズ）。アプリでは `AVAudioEngine` に音を作るノードを置き、試作の `tone()` と `noise()` を同じ値で移す（かすりの音の高さが連続で変わるので、録音した効果音を鳴らす方式では合わない）。音量全体は 0.7。設定の効果音オフに従う。

| 最大 | 5 |

## 10. フィード（何を流すか）

プレイごとにランダム。ただし、サーバーが「そのプレイの並び」を後から作り直せるようにする（ランキングの検証のため）。

- **候補の一覧**：毎日 0 時（日本時間）に関数 `buildSwipePool` が作る

```
swipePools/{yyyy-mm-dd}
  clips: [ { id: string, d: number, u: string } ]   // ステージ ID、難しさ(クリア率を 1000 倍した整数。大きいほど易しい)、作者の uid
```

  - `clip` があり `status == "published"` で、通報で隠れていないもの。急上昇・新着・人気から合わせて最大 3000 本（新着を 30% 入れて、新しい作り手にも遊ばれる機会を作る）
  - 一覧が作れなかった日は前の日の一覧を使う。オフラインでは公式ステージだけの一覧（アプリに同梱）を使い、ランキングには送らない
- **そのプレイの乱数の種**：`useStamina` がスタミナを減らすときに `playId` と `seed`（32 ビット）と一覧の日付を返す
- **並びの作り方**：n 本目は、種と n から作った乱数で、3.3 章の手順で選ぶ。どれを出すかはその時点の連続数で決まるので、同じ種でも遊び方で並びが変わる。サーバーはリプレイから連続数を再現できるので、同じ並びを作り直せる
- 自分とブロックした作者のクリップは、候補から除く（作者は一覧の `u` で分かる。ブロック一覧は送信時に一緒に送り、サーバーも同じ除き方をする）

## 15. ランキング

### 15.1 何を競うか
- **1 プレイの点数**（5 章）。同じ日の中では、その人の一番いい点数だけを載せる
- 表：**今日**（日本時間の 0 時で切り替え）、**昨日**（確定した結果）、**歴代**（その人の最高点）
- 上位 100 人と、自分の順位（「あなたは 1,234 位」）を出す
- 名前は本編のランキングと同じ（匿名の言葉 2 つ＋番号、または投稿者名。`PlayerHandle` を使う）
- プレイ終了画面に順位を出す：「今日 38 位」「自己ベスト更新！」。上位 100 に入ったら派手に出す

### 15.2 点数を確かめる（ズル対策）
点数は端末で計算するので、そのままでは改造した点数を送れてしまう。本編のランキング（`submitScore`）と同じく、**サーバーでリプレイから計算し直した点数だけを載せる**。

- アプリは 1 プレイの記録を送る：`playId`、各クリップの操作記録（GO 中の 60 ステップまでの動き、プレイ中の 1200 ステップまでの動き、スキップしたか）、ブロック一覧。クリップの ID は送らない（サーバーが種と一覧から作り直す）
- 記録の読み方（`DanmakuCore` の `SwipeRun`）：1 本ごとに「早送り → 安全な位置 → GO の動き → 1 ステップずつ（かすり → コンボ・ボム → 被弾なら終了 → 最後のステップかステージ終了ならクリア）」。動きが尽きたとき、スキップならそこでスキップ、そうでなければ「途中でやめた」ことにして計算を止める（それまでの点数は残る）。1200 ステップ・60 ステップを超えた分は使わない
- `submitSwipeRun` がやること：
  1. `playId` が本人のもの・2 時間以内・まだ送っていないことを確かめる
  2. 種と候補の一覧から並びを作り直し、1 本ずつ：`at` まで早送り → 安全な位置に置く → GO 中の動きを当てる（弾は止めたまま）→ 1200 ステップ計算。かすり・コンボ・ボム・クリア・被弾を数え、5 章の式で点数を出す
  3. 被弾したところで終わり。出た点数をその日の記録として保存する
- 送るのは、**その日の自分の記録を超えたとき**だけ（サーバーの計算を減らすため）。送信の間隔も本編と同じく制限する
- 端末の点数とサーバーの点数が違ったら、サーバーの点数を使う（ずれた回数はログに残し、計算のずれを直す手がかりにする）
- 弾の動きはすでに本編のランキングで端末とサーバーが一致しているので、同じ計算に「かすり」と点数を足す。両方に同じテスト用の記録を通して、点数が 1 桁も違わないことを確かめる

### 15.3 保存の形
点数は上限なしなので、そのままでは Firestore で並べ替えられない。**桁数（3 桁、0 埋め）＋数字**の文字列にして並べる（例：`017` + `16532314134240000`）。

```
swipeDays/{yyyy-mm-dd}/scores/{uid}
  key: string        // 並べ替え用（桁数＋数字）
  score: string      // 10 進の数字
  streak: number
  clips: number
  a, n, num, name    // 名前（本編と同じ）
  createdAt: timestamp
swipeBest/{uid}      // 歴代（同じ形）
swipeReplays/{yyyy-mm-dd}_{uid}   // その日の記録のリプレイ（あとで確かめられるように）
```

- 順位は `key` が自分より大きい数を数える（本編と同じ数え方）
- 桁数が 999 桁を超えるほどの点数は、連続数百本が必要なので考えない（超えたら 4 桁に増やす）

### 15.4 スタミナとの関係
- スタミナを使ったプレイだけが種をもらえる。種がないプレイ（オフラインなど）はランキングに送らない
- 回復ドリンクや無限スタミナパスで挑戦の回数は増える。1 回の点数がお金で増えることはないが、回数が多いほど最高点は出やすい（16.4 章で割り切ると決めた）

### 16.2 App Store の決まり（審査で見られる）
- 購入画面に、**価格・期間（1 か月）・自動更新されること・解約しない限り更新されること**をはっきり出す

- 今は RevenueCat を匿名の ID で使っている。**ログイン時に `Purchases.logIn(Firebase の uid)` を呼び、RevenueCat の ID を uid にそろえる**（これまでの購入は RevenueCat が引き継ぐ。既存の購入の復元が壊れないことを実機で確かめる）
- RevenueCat の通知（Webhook）を受ける関数 `revenuecatWebhook` を作り、`users/{uid}.passUntil`（有効期限）を書く。通知の認証用の値は Functions の秘密の設定に入れる
- `useStamina` は `passUntil` が今より後ならスタミナを減らさずに種を返す。念のため、`passUntil` が切れていたら RevenueCat の REST API で一度だけ確かめ直す（通知が遅れたとき用）
- 自動プレイで回し続けるのを防ぐため、加入中でもプレイ開始の間隔は 15 秒以上あける

### 16.4 ランキングの扱い（決定：割り切る）
- パスの人も、全部のプレイをランキングの対象にする（挑戦の回数に上限はつけない）
- ランキングに載るのは 1 日の一番いい点数だけ、という決まりは全員同じ
- 挑戦の回数が多いほど最高点が出やすいことは承知の上で選んだ。β の間に、パスの人とそうでない人の順位の分かれ方を見て、偏りが大きすぎたら見直す

加入数、解約率、加入者の 1 日のプレイ数、ドリンクの売上の変化（パスに食われていないか）、今日のランキング上位 100 人のうちパスの人の割合。

## 17. 作者で絞り込む（追加案）

- クリップの作者名を押すと、**その作者のクリップだけ**が流れる（フィードの右上に「○○ のみ」と出し、×で解除）。
- 仕組み：`useStamina` に任意の `author`（uid）を渡す。サーバーはプレイの記録に `author` を保存し、`SwipeRun.play` の `pool` を `author` で絞ったものにして計算し直す（並びの作り方は変えない。件数が 20 未満なら目標に近い順で全部が候補になる）。
- 同じプレイで同じクリップは出ないので、その作者のクリップを全部遊んだら、そこで終わり（クリア扱い）。
- スタミナは通常どおり 1 消費。
- **全体ランキングには載せない**（自分で易しいクリップだけ作って上位になるのを防ぐ）。作者ごとの専用ランキングは、必要になってから検討。
- ブロックした作者・自分の作者は、これまでどおり選べない。
